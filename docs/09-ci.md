# 09 · CI dual-publish — one-time setup

`/.github/workflows/release.yml` publishes BOTH stores on every tag `v*`:
test (deps from public registries via `UV_NO_SOURCES=1` — CI validates exactly what
consumers install, private git never needed) → PyPI via **trusted publishing (OIDC,
no API token anywhere)** → npm shim → live-registry smoke with
propagation retries. Lockstep guards fail the run if pyproject/package.json versions
don't match the tag.

Until the one-time steps below are done, tag runs fail at the `pypi`/`npm` jobs —
nothing breaks; publish manually (see `docs/worklog/archive/05-packaging.md`)
and re-run the workflow afterwards
(Actions → run → Re-run jobs) for the record.

## 1. PyPI trusted publisher (~2 min, web only)

**Read this before clicking anything.** PyPI allows exactly one registration of a given
`(owner, repository, workflow, environment)` tuple **across the whole site**, not one
per project. Both this repo and `gemini-router` publish from `release.yml` in their own
repo, so they need **two separate publishers, registered from two different project
pages**. Registering the same tuple twice is refused with a banner that names the
project already holding it:

> ⚠ `release.yml` is already registered with gemini-mcp-gateway

That banner is not a failure of your input — it means this exact tuple is taken. If you
see it while adding a publisher for `gemini-router`, you are on the wrong project page:
go back and start from the `gemini-router` project instead.

The publisher lives under the **project**, so a project must exist on PyPI first.
`gemini-router` 0.1.0+ and `gemini-mcp-gateway` both already exist, so both are ready.

### 1a. For `gemini-mcp-gateway` — already registered, do not repeat

Verified present on 2026-10-10: owner `vernikr`, repository `gemini-mcp`, workflow
`release.yml`, environment `pypi`. Nothing to do; the `pypi` job has been publishing
through it since v0.12.1.

### 1b. For `gemini-router` — this is the one still missing

1. pypi.org → sign in → project **gemini-router** (not gemini-mcp-gateway) →
   left sidebar **Publishing** → *Add a new publisher*:
   - Owner (required): `vernikr`
   - Repository name (required): `gemini-router`
   - Workflow name (required): `release.yml`
   - Environment name (optional): `pypi`
2. `gemini-router` repo on GitHub → Settings → **Environments** → New environment:
   `pypi`. The name must match exactly; no secrets go inside it.
3. Re-run the failed release: `gemini-router` → Actions → the `v*` run →
   **Re-run failed jobs**. No new tag needed — 0.1.4 is already built and on PyPI.

`gemini-router/.github/workflows/release.yml` already declares
`environment: pypi` and `permissions: id-token: write`, which is what the OIDC handshake
needs, so no workflow edit is required.

### If you would rather not do the web setup at all

Publish by hand with a **project-scoped** API token — this is how 0.1.3 and 0.1.4 went
out:

```bash
cd gemini-router && rm -rf dist && uv build && uv publish --token "$PYPI_TOKEN" dist/*
```

`rm -rf dist` matters: a stale artifact in `dist/` gets uploaded too and PyPI answers
400 for the version that already exists. The token needs upload rights on the
`gemini-router` project. This keeps working indefinitely, but every release then needs a
human — which is exactly what 1b removes.

### Token hygiene

Both a leaked GitHub PAT and a leaked PyPI token were revoked by registry secret
scanning on 2026-10-10 after the file holding them was exposed. Treat every credential
that has ever lived in a plaintext file as burned, and prefer the OIDC path above: it
mints a short-lived token per run and leaves nothing to leak. A user-scoped token is
worth keeping only for emergencies.

## 2. npm publish token (~2 min)

1. npmjs.com → Access Tokens → **Generate New Token → Granular Access Token**:
   - Packages: `@vernikr/gemini-mcp` only · Permission: **Read and write**
   - expiration: ≤ 90 days (calendar reminder to rotate; automation tokens for CI
     are being restricted for 2FA-bypass — granular + short expiry is the safe lane)
2. GitHub repo → Settings → Secrets and variables → Actions → New repository secret:
   `NPM_TOKEN` = the token value.

Notes:
- `--provenance` is OFF: sigstore attestation requires a PUBLIC source repo (private →
  E422). Re-enable (the job already has `id-token: write`) if the repo goes public.
- Upgrade path (optional): npm Trusted Publishers (npmjs.com → package → Settings →
  Trusted Publisher → GitHub Actions, org `vernikr`, repo `gemini-mcp`, workflow
  `release.yml`) removes `NPM_TOKEN` entirely; needs npm CLI ≥ 11.5.1 in the runner
  (bump `node-version: 24` when switching).

## 3. Release flow after setup (no manual tokens ever)

```bash
# bump versions (lockstep!), commit, tag, push — the workflow does the rest:
sed -i 's/^version = "X"/version = "Y"/' pyproject.toml
sed -i 's/"version": "X"/"version": "Y"/' packaging/npm/package.json
git commit -am "chore: release Y" && git tag -a vY -m "vY" && git push origin main vY
```

Watch: repo → Actions → release. Green `smoke` job = both registries serving Y
(`uvx --from gemini-mcp-gateway==Y gemini-mcp --version` + `npx @vernikr/gemini-mcp@Y`).

## Known quirks (observed 2026-10-10, handled by the workflow)

- npm registry propagation takes ~2–4 min after publish (`ETARGET` until then) —
  smoke retries 8×30s.
- uv caches the PyPI simple index — smoke uses `--refresh`.
- `uv publish`/dist hygiene: always `rm -rf dist` before `uv build` (a stale artifact
  once caused a 400) — the workflow does it.
- Dist name ≠ console script: everything calls `uvx --from gemini-mcp-gateway==V
  gemini-mcp` (the npm shim too).

## Push-CD to production (multi-project pattern from browser-agent)

`release.yml` gained a `deploy` job (`needs: pypi`) calling the reusable
`vernikr/browser-agent/.github/workflows/deploy-ssh.yml@main` with
`{app: gemini-mcp, tag: github.ref_name}`, `secrets: inherit`.

Chain: tag push → test → pypi → deploy → `ssh <ci-key>@YOUR_VPS_HOST "deploy gemini-mcp <ver>"`
→ authorized_keys forced command → `/usr/local/bin/deploy-tools` →
`/etc/deploy-tools.d/gemini-mcp.conf` (`INSTALLER=uv PKG=gemini-mcp-gateway
BIN=gemini-mcp UNIT=gemini-mcp.service STATUS_URL=http://127.0.0.1:8790/healthz
HEALTH_FIELD=version`) → `uv tool install --force --refresh` → `systemctl restart`
→ healthz must report the new `version` (20×1 s) → else automatic rollback to prev.

Repo secrets (set 2026-10-10 via REST sealed box, write-only): `DEPLOY_SSH_KEY`
(per-repo ed25519, pubkey pinned to the dispatcher: no-pty/no-forwarding),
`DEPLOY_HOST`, `DEPLOY_USER`. No local copy of the private key survives.

Server unit change (2026-10-10): `ExecStart=/root/.local/bin/gemini-mcp serve`
(uv-tool binary — the dispatcher's install target; was `/opt/apps/gemini-mcp/.venv/...`)
and `ProtectHome=true` removed (it hides `/root/.local` from the unit; other hardening
kept: MemoryMax=350M, NoNewPrivileges, PrivateTmp, ProtectSystem=full). WorkingDirectory
`/opt/apps/gemini-mcp` + `EnvironmentFile=.env` unchanged → config.yaml/keys/ledger
(`GEMINI_ROUTER_STATE=/opt/apps/shared/gemini-router/state.db`) all preserved.
The rsync path (`scripts/run_remote.sh`) still works for config/src-level changes;
version releases now flow through CD. Backups: `/root/bak/` (authorized_keys + unit).
